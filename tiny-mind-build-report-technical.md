# Building the Tiny Mind Artifact Edition — Technical Report

## What was being ported

Tiny Mind is three single-file, no-build HTML apps that run a small character-level language model entirely in the browser. The Nursery lets you invent a character, ghostwrite a storybook for it, train the 260K-parameter "trainee" live, and export the trained `.bin`. The Microscope inspects any model — probability bars, logit lens, attention heatmaps, neuron highlighting, ablation. The Hunt is an interpretability treasure-hunt: probe the model with a prompt, get falsifiable clues about where a fact is stored, and prove or bust each clue by switching parts off. The weights are Andrej Karpathy's llama2.c TinyStories checkpoints (Eldan & Li). All three already ran from `file://` and GitHub Pages, drove off-thread compute with Blob-based Web Workers, and feature-detected a keyless Claude provider. The stated task was one line: "make the artifact version."

## The task inverted twice

On inspection the port looked trivial. The apps were already about 90% sandbox-native by construction. The one environment-coupled dependency was persistence: `localStorage`, which the claude.ai artifact runtime forbids in favor of an async `window.storage` key-value API. The fix was a feature-detected `Store` that prefers `window.storage`, falls back to `localStorage`, then to memory, backed by a synchronous in-memory cache hydrated once at boot so the existing synchronous read sites did not have to change shape. One correct call, a dozen call sites renamed, done.

Then the sandbox began failing assumptions the apps were built on, one at a time — and almost every failure surfaced empirically, from a pasted console error or a screenshot, not from documentation. The honest shape of the project was not "swap the storage layer." It was "discover the rules of an under-documented runtime by hitting its walls."

## The sandbox restrictions, in the order they broke

**Blob workers are blocked.** `new Worker(URL.createObjectURL(blob))` throws a cross-origin `SecurityError` inside the artifact's `about:srcdoc` frame (origin `claudeusercontent.com`). The entire app died on load, before any of my storage work ran. The README asserted that Blob workers work in artifacts; they do not, and no one had actually run the apps in a real artifact to find out. Worth noting the miss: my prior turn had flagged the *keyless Claude API* as the likely first failure. It wasn't. Blob workers were. The fix is an inline same-thread worker shim — an object that implements `postMessage`/`onmessage`/`addEventListener` and runs the worker source on the main thread via `new Function('self', src)` with a shimmed `self`. The worker code is DOM-free and touches only globals that exist on the main thread, so it runs unchanged; the cost is that compute (including training steps) shares the UI thread. The real Worker is still used where blob workers are allowed, with the shim as a caught fallback.

**DataTransfer is neutered across awaits.** Dropping the model `.bin` and tokenizer one at a time lost the second file, because the drop handler iterated `e.dataTransfer.files` across an `await f.arrayBuffer()`. The browser is free to empty the DataTransfer once event dispatch completes — the first await. Fix: snapshot `[...e.dataTransfer.files]` synchronously. The same trap applies to `items[i].webkitGetAsEntry()` for folder drops.

**Downloads are blocked from nested frames, but not from the top frame.** A probe artifact (built specifically to test the sandbox before committing to the combined build) showed that a nested iframe cannot trigger a download, while the top document can. That produced a workaround I over-engineered: bytes bounced to the shell, which showed a chip the user clicked to supply a gesture. Ken pushed back — twice — and he was right. The top frame's blob download works without a fresh user gesture, so the correct design is: the app frame's Save posts bytes up, the shell downloads immediately, no chip. Two clicks became one.

**Clipboard writes are blocked in frames.** Same probe. Irrelevant once downloads were routed correctly.

**Third-party API fetches are blocked by CSP.** OpenAI and Gemini cannot be reached from inside the artifact; only Anthropic works, via the shell. This is why entering an OpenAI key in the Hunt's detective appeared to "do nothing" — the key was used, the fetch was blocked, and the code fell back to the built-in heuristic. The fallback had been overwriting its own error message, so the failure was invisible; making it persistent and specific was the fix.

**`file://` is a unique opaque origin.** Running the combined file locally by double-clicking fails hard: every `file://` is its own origin, so fetches are CORS-blocked and the shell and its frames are cross-origin to each other. The combined app requires serving over `http` (localhost or a host).

## The combined build: shell, frames, bridge

The three apps were merged into one file (`tiny-mind-mega.html`) without rewriting them. A thin shell provides tabs, a shared model "bay," and file ingest; each app runs byte-intact inside its own `<iframe srcdoc>`, mounted from a `<template>`. Merging rather than iframing would have meant namespacing three codebases that share DOM ids and globals — high-churn and regression-prone — so hard isolation was worth the duplicated engine copies at this scale.

Each frame carries a small bridge script, inert when the app runs standalone (`window.parent === window`). Framed, it polyfills `window.claude` and `window.storage` as RPC calls to the shell over `postMessage`, so the apps' unchanged LLM and storage code believes it is in a full artifact. The shell answers `claude.complete` with the native artifact API when present and a keyless `fetch` to Anthropic otherwise, and answers `storage.*` from its own `window.storage`/`localStorage`/memory backend. Exports bubble up the same channel. The whole trilogy loop closes: a mind trained in the Nursery is exported, auto-joins the shared model table by vocabulary, and opens one click later in the Microscope or Hunt.

Ingest is deliberately format-agnostic. A single drop (or file picker) can be loose `.bin`/`.json` files, a whole folder, or a `.zip` — parsed directly for STORE entries and via the browser's built-in `DecompressionStream` for DEFLATE, no library. Model files are classified by *parsing*, not filename: a strict tokenizer-table walk to exact EOF, else a plausible llama2.c header, so the right vocab-512 trainee pair is picked out of a five-file bundle and the rest is set aside with an explanation. When the combined app is served, the shell eager-loads the known model files (and `replay.json`) sitting beside it, so no dropping is needed; in the sandbox those fetches fail and it falls back to drop.

## Verification discipline

Nothing shipped on inspection. Every change was checked with `node --check` on the extracted page script *and* the worker source, plus focused unit suites run in Node: the storage shim against fake `window.storage` and `localStorage`; the inline-worker shim for bidirectional message routing, retained module state, and load-time error routing; an end-to-end run of the real Nursery worker through the shim against a synthetic checkpoint I built to the `.bin` format (init → ready → set-data → two real training steps with finite loss → export round-trip); the zip parser and model classifier against a decoy-laden bundle; the bridge RPC protocol against a mock shell; the choice-card resolver across a mutating pool; and the Hunt's odds formatter and name-control verdict thresholds. Worker edits use an extract → edit → re-embed cycle with an exact round-trip assertion, because the worker lives as an escaped string literal inside the HTML. Structural checks confirm every layer of the 480 KB combined file parses. The build is reproducible: `patch_apps.py` applies anchored, asserting transforms over the three release files, `build-mega.js` assembles the shell and frames, and both are syntax-checked at build time. Total across the suites at the current build: on the order of a hundred assertions, all green.

## Interpretability, and where the tool's premise strains

One thread deserves its own note because it turned into features. A probe of the trained "Sisi" model showed the model completing "lives in a magic ___" with "tree" at 94.5% but "is a nice ___" with "unicorn" at one in 4.3 million — despite the training data teaching both facts about equally (bigram probabilities 0.96 and 0.92). The cause, confirmed in the worker, is that the Hunt scores an answer as the *product* of the model's per-token probabilities. `" tree"` is one common token; `" unicorn"` is a rare word the 512-vocab tokenizer splits into several pieces, and one weak piece sinks the product. The answer looked ignorant of something it generates fluently. Secondary factors compound it: the predictor word's specificity (`magic` is rare and near-monogamous; `nice` carries strong base-model priors), and a tense mismatch (present-tense probes against past-tense training).

That led to a per-token breakdown display, and to a deeper realization: ablating heads or neurons for the "magic → tree" fact does essentially nothing, because that fact is not stored "about Sisi" at all — it is a local bigram triggered by the word `magic`, which any context completes. The Hunt's evidence is name-centric (attention to the character's name, neuron contrast on the name pieces), so for a non-name-bound fact the detective is handed the wrong evidence and proposes doomed clues, and the child correctly discovers that the clues lie. The fix was a name-control experiment (re-probe with the name swapped; if the answer holds, the fact is not name-bound and there is no treasure to hunt), steering the detective with neuron evidence at the prediction position rather than only the name, and in-app guidance toward *huntable* facts: single-token, name-bound, non-collocation. The honest conclusion is that the Hunt's premise — that knowledge is localized and findable by single-unit ablation — is cleanly true only for a narrow class of facts. That is arguably a feature to teach rather than a bug to fix, and it is a design decision left open.

## Open, and honestly uncertain

Three things could not be verified from outside a live browser and remain empirical: whether the 480 KB combined file pastes under the artifact's size ceiling; whether the keyless Claude path resolves in the current runtime (`window.claude.complete` may or may not exist; the Nursery ghostwriter using the same path is the tell); and whether nested-frame download really is impossible or merely was in the probe. The threshold constants in the name-control verdict (0.5× and 0.15× of baseline) are judgment calls awaiting tuning against real characters. And the standalone deploy assumes a flat `apps/Tiny Mind/` folder with the models and `replay.json` beside the HTML, served over `http`.

## The shape of the work

The project had two distinct halves. The first was a fight with an under-documented runtime, where the apps' bugs were "this capability does not exist here" — blob workers, downloads, clipboard, cross-origin storage, DataTransfer, `file://` — each handled by feature-detecting rather than assuming, and each found by pasting an error rather than reading a spec. The second half, once the thing ran, was different in kind: the bugs became "the machinery is correct but the concept is not legible at the surface." Two mechanisms sharing one word or one panel kept causing confusion — measured probabilities versus an advisor's guesses, replay-mix versus base-eval, a name-fact versus a generic bigram, scientific notation versus "1 in 1,124." That second class is the review a builder cannot do on their own code, and it is the clearer signal that the app is close: when the mechanism confuses the person who built it, that is the tell.

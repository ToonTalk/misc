One-sentence summary

The project evolved from a story-first client-side prototype into a richer web metagame with Astronaut Rescue, Lunar Lander, attachable transparent behaviour cards, live-AI teammate questions, JSON import/export, project switching, and ongoing UI/debug fixes.

Design premise

Narrative frame

The player is a newly hired game developer on their first day. The boss gives an initial assignment: make a game about rescuing an untethered astronaut. After a successful rescue, the boss introduces Lunar Lander as the second project.

Pedagogic frame

The learning model is layered: the player can first assemble a simple working game, then inspect and edit pseudocode, critique playtests, and gradually encounter physics, programming, game design, project management, history, art, and sound.

The strongest metaphor stayed consistent throughout: a sprite has a front side, which is its image, and a back side, which contains composable behaviour cards.

Main characters and roles

  • Boss: gives briefs, milestones, and high-level direction.
  • Scientist: explains motion, momentum, gravity, telemetry, and what needs to be measured.
  • Programmer: converts specialist ideas into transparent behaviour cards.
  • Assistant game designer: explains goals, challenge, win/loss rules, safety thresholds, and feedback loops.
  • Historian: adds historical context about spaceflight, Lunar Lander, Newtonian mechanics, and early computing/games.
  • Artist/animator: supplies or helps specify placeholder sprites and future text-to-image prompts.
  • Sound/music teammate: suggests thrust sounds, success/failure cues, alarms, and feedback sounds.

Prototype evolution

Initial prototype: story-first structure, boss/team, resource unlocking, behaviour cards, Astronaut Rescue canvas, playtesting, and Lunar Lander as a future step.
Conversation repair: team member interactions were expanded from brief unlocks into more substantial greetings, questions, and specialist explanations.
Lunar Lander added: second project with gravity, thrusters, fuel, safe touchdown, and lander telemetry.
UI flow tightened: story/team interactions come before the studio, conversations appear in-place, and resources/checklists were made clearer.
Live AI added: users can enter OpenAI, Gemini, or Claude keys, choose model names, optionally cache keys locally, and ask free-form questions of team members.
Live AI prompt iterations: fixed role framing, shortened responses, removed jargon, exposed prompts for debugging, added metagame context, and preserved team-any-order navigation.
Attachment debugging: behaviour attachment repeatedly failed until a state-reset bug was identified; resetting the playtest had been reloading stale localStorage and erasing just-attached cards.
Import/export added: JSON export was already present; import was added and later fixed to preserve behaviour code and reviewed state.
Project switching added: the user can return from Lunar Lander to Astronaut Rescue and vice versa after import or normal play.
Gauge and syntax cleanup: several iterations addressed telemetry visibility, current-project switch buttons, and recurring template-string syntax errors.

Current known design decisions

  • The game should remain client-side for now; live AI is optional and key-based.
  • The player should be able to start building before every behaviour is available, then discover gaps through playtesting.
  • Team members can be visited in any order during the team phase.
  • The scientist explains ideas; the programmer creates behaviour cards from those ideas.
  • Wrong-object attachments should be allowed as experimental mistakes, not blocked.
  • Behaviour labels should not clutter the play area during playtests.
  • Live AI should be brief, plain-spoken, and context-aware.
  • Imported/exported state must distinguish between unlocked behaviours and attached behaviours.

Open issues and useful next fixes

  2. Prototype identity: “revised prototype” means the specific named checkpoint linked in a response; “latest generic prototype” means first-day-game-studio-prototype.html, an alias repeatedly overwritten with the current recommended version.
  3. Import summary: import should show a clear post-import report: unlocked behaviours, attached behaviours per object, current project, and whether Lunar Lander is available.
  4. Source-control style history: the project now needs a more disciplined changelog or version number in the UI to stop confusion between links and local browser caches.
  5. Automated smoke tests: add small in-browser tests for attach, import, switch project, run rescue, run lunar, and show gauges.

What “revised” versus “latest generic” means

Revised prototype is the specific named file linked for that response, such as first-day-game-studio-prototype-gauge-switch-clean.html. It is a checkpoint. It should not change after being created.

Latest generic prototype is first-day-game-studio-prototype.html. It is intended as a convenience link to the newest recommended version, but it has been overwritten many times. That makes it easy to open, but worse for debugging because it hides which exact version you are testing.

Best practice from here: use the named checkpoint for testing and mention its filename when reporting bugs. Use the generic file only as a convenience shortcut.

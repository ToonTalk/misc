Abstract

A new experimental technique for automatically generating compilers from interpreters is applied to a Prolog interpreter. The Prolog interpreter called LM-Prolog was implemented in Lisp, with the dual purpose of supporting a partial evaluator for Lisp programs called Partial and making the implementation itself a suitable input to Partial. A partial evaluator takes programs and generates more efficient, less general versions of them. Partial is being applied to LM-Prolog to produce specialized versions of Prolog for a given database of assertions or programs. The plan is to apply Partial to LM-Prolog together with the database corresponding to Partial to produce an efficient Lisp version of Partial. Then the Lisp version of Partial will be given to itself together with the code for LM-Prolog, which should produce a specialized partial evaluator for LM-Prolog: in other words, a compiler from LM-Prolog programs to Lisp.

1. An Overview of the Lisp Machine Prolog Project

LM-Prolog, Lisp Machine Prolog, was developed with one purpose in mind: to support a partial evaluator capable of partial evaluating the Prolog. A partial evaluator can be used to make source-to-source optimizations, to generate new programs by intertwining old programs, to expand macros, to support language extensions, and to compile programs written in embedded languages.

The implementation is constrained to be as simple, side-effect free, and modular as possible. In order to partial evaluate it effectively, it should use the Lisp stack rather than representing a Prolog stack with an array or list. Pure Prolog is inadequate for implementing a partial evaluator and various evaluable predicates are needed. On the other hand, all the evaluable predicates need to be implemented in a clean way for the partial evaluator to partial evaluate their use.

Satisfying these constraints would be impossible without very rich computational resources. The Lisp Machine, a single-user large address space computer supporting a powerful modern Lisp dialect, was instrumental in this research.

2. Partial Evaluation of Lisp Programs

Partial evaluation in Lisp can be defined simply as evaluating a program after some information about its arguments or environment is already known. The paper writes this relationship as an equivalence between evaluating a partially evaluated program and evaluating the original program in the same environment.

Writing partial evaluators is simple in outline, but writing quality partial evaluators is challenging. One measure of quality is the relative effectiveness of input and output. Secondary measures include the effectiveness of the partial evaluation process itself, the readability of the output, and the simplicity and ease of use of the evaluator.

If such an interpreter is partial evaluated where the user program is known but the input is unknown, the result is a Lisp program that behaves like the user program.

      


      

        
3. Why Write a Partial Evaluator for Lisp in Prolog?

        
Prolog is well suited for writing partial evaluators. The main reason is that Prolog normally runs with partially instantiated data. In LM-Prolog, partially instantiated structures and database assertions can represent partial knowledge about arguments, values, types, and relations.

        
Prolog's theorem prover can make use of many kinds of facts. It is especially useful in handling conditionals: the then branch can be evaluated under the assumption that a predicate is non-nil, while the else branch can be evaluated under the assumption that the predicate is nil. Prolog's ability to use programs in multiple ways greatly simplifies the evaluator.


        
4. Why Not Just Write a Partial Evaluator for Prolog in Prolog?

        
If Prolog is so well suited for partial evaluation, one may wonder why not write a partial evaluator for Prolog instead. One reason is that it is probably more difficult to achieve the same kinds of optimizations that partial evaluators perform for Lisp. Even if a quality partial evaluator for Prolog were developed, it would produce more effective, less general Prolog predicates; the problem remains of compiling them effectively.

        
Lisp is an ideal object language. Prolog is a little too high-level, and the engineering support in major Lisp dialects is superior to contemporary Prolog implementations. A double partial evaluation scheme is appealing: first partial evaluate a Prolog program to Prolog, and then partial evaluate the result to Lisp.

      


      

        
5. The Implementation of LM-Prolog

        
LM-Prolog is based upon a Lisp function called Prove. Prove takes a statement containing free variables and constructively proves that values exist for the variables such that the statement is true. It either fails or sets a subset of the value cells of the free variables and returns a stream of additional proofs.

        
Prove works by unifying the statement to be proved with the head of each assertion in the database. For each successful unification, it proves the conjunction of statements in the body of the assertion in the environment of the unification.


        
6. The Partial Evaluator

        
Partial mirrors Lisp's eval. Constants evaluate to themselves. Variables evaluate to their bindings, or to themselves if unbound. Forms are evaluated by applying the definition of the function to the arguments. The evaluator keeps special forms and primitive functions to an absolute minimum: cond, let, eq, typep, first, rest, replace-first, and replace-rest.

        
Another source of power comes from a small set of program transformations. These are applied because they produce equivalent code that is easier to further partial evaluate.

When faced with a problem involving user functions, it generalizes the problem, makes up a name for a function, and temporarily adds an advertisement to the database describing the conditions for using the new function.

8. Partial Evaluation of Prolog

        
The partial evaluation of LM-Prolog consists mainly of partial evaluating unify and prove. In the typical case, during partial evaluation at least one of the two arguments to unify is known. Even if both arguments are known, the partial evaluation is not trivial because the arguments can contain Prolog variables that may or may not be bound at run time.

        
The prove function can be partial evaluated where there is partial knowledge about the statement to be proved and partial knowledge about the database. Each predicate in LM-Prolog is either static or dynamic. Static predicates have their assertions already given; dynamic predicates can change unpredictably and are left as calls to prove for run-time evaluation.

9. Future Research

        
The immediate directions for this research are clear: partial evaluate calls to prove and unify, then partial evaluate Partial, and then partial evaluate the result of partial evaluating Partial with itself and LM-Prolog. In the longer term there is the possibility of partial evaluating languages written in LM-Prolog, such as Intermission and Uniform.
